# 0022. Offer purchase help and system refunds, and pin transactions to a bundled root

- **Status:** Accepted
- **Date:** 2026-10-26
- **Feature / area:** `ForeverAlonePoker/Features/SkinStore/Help`, `ForeverAlonePoker/Shared/Skins` (`PurchaseService`, `TransactionCertificateValidator`, `SupportContact`, `SkinStore`), `ForeverAlonePoker.xcodeproj/xcshareddata/xcschemes/ForeverAlonePoker.xcscheme`

## Context

The card store (tdr/0012) sells non-consumable skins with StoreKit 2. Several things around purchases were missing:

- **Help and refunds.** Apple's HIG (*Apple In-App Purchase › Providing help*) asks for a help screen before a refund, listing Missing a Purchase, Frequently Asked Questions, Request a Refund, Submit Feedback and Contact Us. The refund list shows each purchase's image, name and original purchase date, and enters the **system** refund flow (`Transaction.beginRefundRequest(for:in:)`) without anything standing in the way. The action is titled plainly ("Request a Refund"). The app never characterises Apple's refund policy; it may link to Apple's support article instead. The system sheet and its "Your request has been submitted" confirmation belong to Apple and are not replicated.
- **Payments switched off.** The HIG asks to show the store only when `AppStore.canMakePayments` is true, or to explain why it is not available.
- **Pinning.** *Setting up StoreKit Testing in Xcode* says to validate locally signed data against the StoreKit test certificate, chosen with `#if DEBUG` `StoreKitTestCertificate` / `#else` `AppleIncRootCertificate`. Modern StoreKit 2 transactions are JWS whose `x5c` chain ends at **Apple Root CA – G3**. The legacy "Apple Inc. Root" signs only the deprecated PKCS#7 receipt.
- **Scheme setting.** The shared scheme pointed its StoreKit configuration at `../../SkinStore.storekit`, but the file lives in `StoreKit/SkinStore.storekit`.
- **Contact.** Support mail goes to `jalmeidatorres18@gmail.com`.

## Decision

1. **Help screens** live inside the SkinStore feature (`Features/SkinStore/Help`), so no feature imports another:
   - `PurchaseHelpView` ("How can we help?") is reached from a Help button in the store's toolbar and a footer link. Its rows:
     - **Missing a Purchase** (`MissingPurchaseView`) explains Apple Account ownership and Ask to Buy, and offers *Restore Purchases*: the immediate alternative to a refund.
     - **Frequently Asked Questions** (`PurchaseFAQView`).
     - **Request a Refund** (`RefundRequestView`).
     - **Submit Feedback** and **Contact Us** open a `mailto:` from `SupportContact`, with only the app and OS versions prefilled. When no mail app accepts it, an alert shows the address with a Copy button.
   - The footer links Apple's "Request a refund for apps or content that you bought from Apple".
2. **Refund flow.**
   - `PurchaseService` gains `purchaseHistory()` and `requestRefund(for:)`. `purchaseHistory()` returns the latest trusted transaction per product from `Transaction.all`, newest first, refunds included. `requestRefund(for:)` presents the system sheet on the foreground `UIWindowScene` and maps `.success` → `.submitted`, `.userCancelled` → `.cancelled`, and `Transaction.RefundRequestError` → `PurchaseError.refundUnavailable`.
   - `SkinStore` passes both through and adds `item(forProduct:)` to name rows.
   - `PurchaseHelpModel` holds the rows and per-transaction refund state (`requesting`, `submitted`, `failed`). Revoked rows show "Refunded" and cannot be requested again.
   - Ownership never changes in the help screens. A granted refund arrives as a revoked `Transaction.updates` entry, and the existing `SkinStore.observeTransactions` path (tdr/0012) removes the skin.
3. **Payments gate.** `PurchaseService.canMakePayments` (`AppStore.canMakePayments`) is read in `SkinStore.start()`. When it is false, `BuyButton` hides and the store footer explains that purchases are turned off. Owned skins, equipping and restore keep working.
4. **Transaction pinning.**
   - `TransactionCertificateValidator` checks every StoreKit-verified transaction's `jwsRepresentation`:
     - the `x5c` chain is evaluated with `SecTrust` against **only** the bundled root, with no network fetches and at the transaction's `signedDate`;
     - the ES256 signature is checked against the leaf key.
   - The root is chosen at compile time:
     ```swift
     #if DEBUG
         let certificate = "StoreKitTestCertificate"
     #else
         let certificate = "AppleIncRootCertificate"   // contains Apple Root CA - G3
     #endif
     ```
   - A transaction that fails, or a missing `.cer`, is **denied**: finished and never granted, exactly like StoreKit's own `.unverified`. This applies to purchases, `currentEntitlements`, `updates` and the purchase history.
   - The two `.cer` files are added to `ForeverAlonePoker/` by hand. They are auto-included as resources and are not generated by any tool.
5. **Scheme.** The StoreKit configuration reference is `../../StoreKit/SkinStore.storekit`.

## Consequences

- Players get help, a restore and a one-tap path into Apple's refund sheet without leaving the app, and support mail reaches one address.
- **Debug builds only trust Xcode's StoreKit testing.** A Debug build run against the sandbox (scheme StoreKit configuration set to *None*) or TestFlight data signed by Apple grants nothing. Use a Release build for sandbox and TestFlight testing. Release builds without `AppleIncRootCertificate.cer` grant nothing at all, which makes a forgotten file obvious before release.
- `PurchaseService` conformers (`StoreKitPurchaseService`, `FakePurchases`, the preview `ScriptedPurchases`) implement three more members.
- Follow-up:
  - App Store Server Notifications V2 for refunds remain planned (tdr/0012, 7).
  - A consumption-information response to `CONSUMPTION_REQUEST` could be added there.

## Alternatives considered

- **Our own refund form or confirmation step.** Forbidden by the HIG: the system flow must not be replicated or blocked.
- **Validating the legacy PKCS#7 app receipt** with Apple Inc. Root. It is deprecated since iOS 18 and needs an ASN.1/PKCS#7 parser, while StoreKit 2 already delivers signed JWS.
- **Logging pin failures without denying.** It is safer against odd test-environment chains, but a pin that never denies proves nothing. The owner chose to deny.
- **Help as its own feature folder.** Help needs the store's state and is reached only from the store; a separate feature would have to import SkinStore.

## Test strategy

- `ForeverAlonePokerTests/Shared/Skins/TransactionCertificateValidatorTests`: the pinned root passes; another root, a tampered payload, a missing `x5c`, no bundled certificate and garbage are all denied. Fixtures are a self-signed P-256 certificate and JWS built at test time (`Support/JWSFixtures.swift`, `TestCertificateAuthority`).
- `ForeverAlonePokerTests/Features/SkinStore/PurchaseHelpModelTests`:
  - rows are named from the catalog and sorted newest first;
  - an unknown product shows its id;
  - a refunded row is not requestable;
  - submitted, cancelled and failed refund states;
  - a missing purchase restores and reloads;
  - `SupportContact` builds the `mailto:` URL.
- `SkinStoreTests`: `canMakePayments` is reported after start; `item(forProduct:)`.
- Fakes: `FakePurchases` gains `history`, `refundResult`, `refundRequests` and `canMakePayments`.
- Manual, with `StoreKit/SkinStore.storekit` active in the scheme and `StoreKitTestCertificate.cer` in the bundle:
  - buy a set, then go to Card store › Help › Request a Refund and check the row shows its art, name and date;
  - submit the system sheet;
  - in the Transaction Manager, refund it and check the set reverts and the row shows "Refunded";
  - remove the `.cer` and check purchases are denied;
  - Screen Time › Content & Privacy › In-App Purchases: Don't Allow shows the explanation;
  - Contact Us opens Mail.
